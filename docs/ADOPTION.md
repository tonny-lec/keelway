# チームへの導入と測定

## 最初の接続

既存リポジトリを一つ選び、最近の通常変更と実際に困った変更を使って基線を作る。
現在のCI、開発環境、所有者、障害対応、承認を把握し、重複する手順は既存のものへ接続する。
初回から全チームに同じSLO、言語、テスト数、提供頻度を課さない。
プログラムや業務固有の要件は既存の専門家と方針から得る。

| 段階 | 行うこと | 次へ進める証拠 |
|---|---|---|
| 接続 | 実コマンド、作業地図、所有者を登録 | ローカルの代表変更を再現・検証できる |
| 試用 | 通常変更、軽微修正、重要変更で使う | 完了判定が実態と一致し、過剰な工程がない |
| CI接続 | 保護された検証定義、SHA、レビュー、成果物を接続 | 別環境でも再現し、未実行を失敗として扱える |
| 提供へ接続 | 観測、段階提供、回復、所有者を接続 | 対象環境でのリハーサルと効果確認 |
| 改善 | ボトルネックを一つずつ改善 | 速度・品質・運用負担を同時に見て改善が確認できる |

期間はプロジェクトの規模・変更頻度に合わせる。上記は導入の提案であり、各企業の制度の再現ではない。

## 所有と会話

利用者の成果、変更、レビュー、運用、ハーネス保守の責任者を記載する。少人数なら兼務できる。
共有の改善時間には、レビュー待ち、再作業、障害、手作業の負担から最も大きいものを選ぶ。
一つの改善に所有者と完了条件を持たせる。日次の形式的な報告を自動生成することを目的にしない。
問題が見つかった人を責めず、早く見つけて回復できる構造を改善する。

## 指標の契約

以下は [DORAの2026年1月更新の定義](https://dora.dev/guides/dora-metrics/) を参照した測定項目。
コード量や個人のランキングには使わず、一つのアプリ／サービスの改善に使う。

| 指標 | 基本定義 | 必要なデータと注意 |
|---|---|---|
| 変更リードタイム | コミットから本番提供まで | commit SHA・時刻と実提供時刻。PR作成からの時間とは分ける |
| 提供頻度 | 単位期間の本番提供数／間隔 | 一つの提供を多リージョンの実施回数で水増ししない |
| 提供失敗からの復旧時間 | 失敗した提供からサービス復旧まで | 影響開始・復旧時刻。全種類の障害のMTTRと混ぜない |
| 提供失敗率 | 即時介入が必要だった提供／全提供 | hotfixやrollbackが必要な判定を明文化する |
| 提供の再作業率 | 本番障害に伴う予定外の提供／全提供 | 計画済みの機能提供と区別する |

各指標に、所有者、観測窓、サービス、時間帯、集計単位、欠測の扱い、分母、出典を付ける。
平均だけでなく中央値と尾の分布も必要に応じて見る。提供がない期間の失敗率は0%ではなく対象なし。
復旧未完了の障害を集計から黙って落とさず、未完了件数と観測期間を出す。
本配布物は本番の測定データを取得しないため、実際のDORA値は算出していない。

併せて利用者の成功率・SLO・レビュー待ち時間・フレーク率・手作業時間・タスク成功あたり費用を必要に応じて測る。
速度だけ上がって再作業や障害が増えた場合は改善と判定しない。

## ハーネスの変更を評価する

モデル、SKILL、重要パス、必須チェック、承認との接続を変える場合は代表ケースで再確認する。
旧版と新版を同じ入力・環境で比較し、成果、重大失敗、時間、費用、確認回数、変更範囲を記録する。
難しい評価は作者の答えを渡さず、独立した評価者に生の依頼と成果を渡す。
モデルの確率的な挙動を見る場合は複数回とholdoutを使い、実行数を記録する。
未実行ケースを「対応済み」の一覧から除外せず、未実行と明記する。

変更に失敗した場合は、評価で実証された問題を狭く直す。単発の失敗を全作業共通の承認・テスト義務にしない。
使われない文書とゲートを整理し、初回起動とフィードバックまでの時間が延び続けないようにする。
