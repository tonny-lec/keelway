# 運用と組織の学習

## 障害対応

まず利用者影響、開始時刻、範囲、直近の変化、当番・指揮系統、使える復旧手段を把握する。
ログ・グラフの観測と仮説を分け、影響を小さくする最短の可逆な対応を選ぶ。
既に許可された緊急復旧は、ハーネスの書類作成を待たせない。必要な最小の安全確認を行い、経緯と省略した検証を残す。
障害対応の依頼だけを、関係者への自動送信や本番破壊の許可と見なさない。
本番での検証は負荷や副作用に上限を付ける。復旧したら利用者経路・データ・監視で確認する。
その後に証拠記録を補い、恒久修正は通常の検証経路を通す。

## SLOとエラーバジェット

利用者の成功を表すSLI、対象母集団、時間窓、目標、データ源を選ぶ。
ビジネス要件とコストに基づくSLOをチームで合意する。全サービスに同じ99.99%を課さない。
例: 有効要求の成功率SLOが99.9%なら、対象100万要求で許容する失敗は1000要求。
これは説明用の値であり推奨目標ではない。
バジェット悪化時に、どの機能提供を調整し、どの信頼性作業を優先し、いつ通常に戻るかを事前に決める。
データがない状態をバジェット残ありと扱わない。警報には対応可能な手順と所有者を付ける。

## 事後分析

顧客影響、時系列、検知・緩和・復旧、寄与要因、働いた防御、働かなかった防御を記録する。
個人の注意力を原因や対策の終点にしない。テスト、設計、観測、手順、権限、標準経路のどこを変えると再発を減らせるか考える。
改善には所有者、完了条件、優先順位、確認日を付ける。文書だけで完了にせず効果を後から確認する。

## 組織としての運用

サービスまたは価値の流れに、利用者の成果から運用まで責任を持つ所有者を置く。
一人がすべてを行う必要はないが、引継ぎ時の責任の空白をなくす。
共通基盤チームは起動・テスト・観測・提供を簡単にする標準経路を提供する。
例外には理由・担当・見直し期限を残し、同じ摩擦が繰り返されるなら標準を改善する。
変更を小さくし、WIPはチームの容量とボトルネックに応じて制御する。
レビュー待ちを放置せず、設計議論は必要な判断者で解消する。

| 役割（兼務可） | 決めること／残す成果 |
|---|---|
| 成果の所有者 | 利用者価値、優先順位、受入条件 |
| 変更の作者 | 最小の変更、検証、引継ぎ |
| レビュー担当 | 契約、保守性、重要なリスクの別視点の評価 |
| 運用・提供の所有者 | 観測、復旧、提供方針、障害対応 |
| ハーネス保守担当 | 手順とツールの実効性、評価、更新 |

## 測定と改善

サービス単位で、コミットから本番までの時間、提供頻度、失敗した提供からの復旧時間、
提供失敗率、障害に起因する予定外提供の割合を定義する。指標の定義と版は
[DORAの一次資料](https://dora.dev/guides/dora-metrics/) に合わせ、分母・期間・対象を固定する。
併せて利用者成果、SLO、レビュー待ち、フレーク率、手作業の負担、成功タスクあたり費用・時間を必要な範囲で見る。
個人の順位、コミット数、コード量やトークン量だけで生産性を評価しない。
対象外や欠測はゼロにせず、別表示する。アプリの性質が違うチームを無条件に比較しない。

一度に最も制約になっている箇所を一つ改善し、基線との違いを確認する。
ハーネス自体にもこのループを使う。新たな普遍ルールを増やす前に、現実的な評価で効果を確認する。
モデル・指示・ツールの変更時は代表作業と重大失敗ケースを再実行する。
自動化は取り除いた負担より大きな保守負担を生まないかを観察し、不要なゲートは根拠を残して簡素化する。
