# 実装・テスト・レビュー

## 機能と修正

既存の責務・エラー処理・公開契約に合わせる。新たな抽象化は具体的な複数用途があるときに導入する。
不具合は入力→分岐→状態→出力を追い、最小の再現を作る。観測した事実と原因仮説を分ける。
根本原因を直し、必要な回帰テストを残す。既存不具合がある場合は変更前後の結果を区別する。
テストしにくい境界は依存注入・小さな関数等で扱えるか検討するが、依頼と無関係な全面改修をしない。

## リファクタ・依存更新・保守

維持すべき振舞いを固定し、構造変更と挙動変更を可能なら分ける。利用側、シリアライズ、互換性も確認する。
依存更新ではlockfile、変更履歴、公開API差、推移依存、再現可能なインストールを確認する。
性能・費用・保守性の改善は変更前後を同じ条件で比較する。不要なコード・フラグの削除も所有者と利用状況に基づく。

## 検証を選ぶ

| 変更の性質 | 必要になる証拠の例 |
|---|---|
| 純粋な計算・分岐 | 境界値、無効入力、プロパティ、不変条件のunit test |
| DB・ネットワーク境界 | 実際のアダプタのintegration test、部分失敗、期限、再試行 |
| 公開API・イベント | consumer/provider contract、旧版・未知フィールド、順序・重複 |
| 利用者の主経路 | 少数のE2E、アクセス可能性、空・読み込み・失敗状態 |
| 並行処理 | 順序、競合、キャンセル、資源の解放、冪等性 |
| 見た目 | 対象viewportの実画面、キーボード・フォーカス、視認性 |
| 文書・設定 | 実際に使う例、リンク、構文、読み手の手順の成立 |

速い局所テストで反復し、境界と受入条件に必要な統合確認へ広げる。網羅率100%やE2Eの数を普遍的目標にしない。
mockは境界を制御するために使い、実際のI/O契約が変わるなら実アダプタも確かめる。
テストが元の不具合で失敗するか、少なくとも仕様違反を検出するかを見る。実装を書き写した期待値を避ける。
テスト0件・スキップ・手動確認・実行不能を成功と混同しない。ハーネスは終了コードしか自動解釈できないため、
ログを確認してテスト件数と意味を判断する。フレークは原因、担当、期限付きの対応を残す。

## レビュー

依頼がレビューならまず対象差分と影響経路を調べ、問題の根拠を成果にする。依頼されていない修正はしない。
自分の実装を確認するときも、最終差分、呼び出し側、データ、失敗経路、検証結果から評価する。
有効な指摘には「どの入力／条件で」「どこが」「どう壊れる」「影響」「根拠」を入れる。
阻害する不具合、改善提案、好みを区別する。自動整形で解決する議論はCIへ寄せる。
独立レビュー担当には依頼・差分・契約・生の検証結果を渡し、作者の結論を正解として与えない。
指摘のない結果にも対象と確認限界を付ける。レビューの量を品質指標にしない。

## 引継ぎとPR

変更が必要だった理由、利用者から見た結果、検証証拠、互換性、提供上の注意だけをレビュー可能な量にまとめる。
既存PRテンプレートを使う。大量の思考過程や放棄した案は残さない。未確認を隠さず、必要な担当と次の行動を示す。
コードの健康が改善し、契約を守り、影響に見合う証拠がある変更を前へ進める。
